# Паттерн Стратегия (Strategy)

## Описание

**Стратегия (Strategy)** — поведенческий паттерн проектирования, который определяет семейство алгоритмов, инкапсулирует каждый из них и делает их взаимозаменяемыми. Стратегия позволяет изменять алгоритм независимо от использующих его клиентов.

## Проблема

```
Клиент                        Платёжные системы
┌──────────────────────┐     ┌──────────────────────────────────────┐
│ PaymentContext       │     │ VtbPay                               │
│                      │     │ PayPal                               │
│ Pay(amount)          │───→ │                                      │
│                      │     │   1. Какой API вызвать?              │
│                      │     │   2. Как обработать платёж?          │
│                      │     │   3. Как вернуть название метода?   │
└──────────────────────┘     └──────────────────────────────────────┘
```

**Недостатки:**

- **Жёсткая привязка**: клиент жёстко связан с конкретной реализацией платёжной системы (например, `VtbPay`), что затрудняет добавление новых способов оплаты
- **Дублирование логики**: при поддержке нескольких способов оплаты клиент содержит условные конструкции (`if`/`switch`) для выбора алгоритма, что разрастается при добавлении новых стратегий
- **Смешение ответственности**: клиент отвечает не только за бизнес-логику, но и за выбор конкретного алгоритма оплаты
- **Нарушение принципа открытости/закрытости (OCP)**: добавление нового способа оплаты требует изменения клиентского кода

> ✅ Клиент должен вызвать один метод `Pay()` — а не знать о `VtbPay`, `PayPal` и их API.  
> ❌ Проблема — когда клиент жёстко привязан к конкретному алгоритму и содержит логику выбора.

## Решение

Стратегия — интерфейс, который описывает общий контракт для всех алгоритмов, а контекст делегирует выполнение выбранной стратегии:

```
Клиент              Контекст                  Стратегии
┌──────────────┐   ┌──────────────────┐     ┌─────────────────────┐
│ Client       │   │ PaymentContext   │     │ IPaymentStrategy    │
│              │   │                  │     │  ├─ VtbPay          │
│ Pay()        │──→│ Pay()            │──→ │  └─ PayPal          │
│              │   │                  │     │                     │
│              │   │ SetPaymentStrategy│     │ Pay(amount)         │
└──────────────┘   └──────────────────┘     └─────────────────────┘
```

**Контекст** — хранит ссылку на текущую стратегию и делегирует ей выполнение платежа.  
**Стратегия** — интерфейс `IPaymentStrategy`, описывающий общий контракт для всех способов оплаты.  
**Конкретные стратегии** — `VtbPay`, `PayPal`, реализующие разные алгоритмы оплаты.

> Клиент выбирает стратегию и передаёт её в контекст: `paymentContext.SetPaymentStrategy(payPal)` — контекст делегирует выполнение выбранной стратегии, не зная деталей её реализации.

### Как работает

```
Клиент:
  var paymentContext = new PaymentContext(vtbPay);
  paymentContext.Pay(amount: 2500m);

  paymentContext.SetPaymentStrategy(payPal);

  paymentContext.Pay(amount: 15000m);

Контекст внутри:
  1. Валидация: amount > 0
  2. Делегирование: _paymentStrategy.Pay(amount)
  3. Вывод результата с названием метода оплаты
```

**Упрощение изменения алгоритма:**

```
Без стратегии (клиент выбирает алгоритм):
  if (method == "VtbPay")
      vtbPay.Pay(amount);
  else if (method == "PayPal")
      payPal.Pay(amount);
  // при добавлении нового способа — ещё один if/switch

Со стратегией (замена через контекст):
  paymentContext.SetPaymentStrategy(payPal);
  paymentContext.Pay(amount);
```

## Структура

| Компонент | Описание | Пример |
|-----------|----------|--------|
| **Context** | Хранит ссылку на стратегию и делегирует ей выполнение | `PaymentContext` |
| **IStrategy** | Интерфейс, описывающий общий контракт алгоритма | `IPaymentStrategy` |
| **Concrete Strategies** | Конкретные реализации алгоритмов | `VtbPay`, `PayPal` |
| **Client** | Создаёт контекст и стратегии, переключает их | `Client` |

## Преимущества

- **Взаимозаменяемость алгоритмов**: стратегии можно менять во время выполнения без изменения контекста
- **Снижение связанности**: контекст не знает о конкретных реализациях, а только об интерфейсе `IPaymentStrategy`
- **Устранение условных конструкций**: логика выбора алгоритма выносится из клиента в отдельные классы
- **Расширяемость (OCP)**: новые способы оплаты добавляются как новые классы, без изменения существующего кода

## Когда использовать

- Нужно использовать разные варианты алгоритма в зависимости от условий
- Алгоритм должен переключаться во время выполнения программы
- Есть множество похожих классов, отличающихся только поведением
- Нужно изолировать бизнес-логику от деталей реализации алгоритмов

## Связь с другими паттернами

- **State** — State меняет поведение объекта при изменении состояния, а Strategy позволяет менять алгоритм извне
- **Factory Method** — фабрика может создавать конкретные стратегии для передачи в контекст
- **Decorator** — Decorator изменяет поведение объекта, оборачивая его, а Strategy — заменяет алгоритм целиком

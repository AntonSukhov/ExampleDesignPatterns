# Паттерн Фасад (Facade)

## Описание

**Фасад (Facade)** — структурный паттерн проектирования, который предоставляет простой унифицированный интерфейс к сложной подсистеме, скрывая детали её устройства.

## Проблема

```
Клиент                    Подсистема
┌──────────────┐         ┌──────────────────────────────────────┐
│ Client       │         │ FoundationService                    │
│              │         │ RoofService                          │
│ BuildHouse() │───────→ │ FloorService                         │
│              │         │                                      │
│              │         │   1. Вызываем BuildFoundation()      │
│              │         │   2. Вызываем BuildRoof()            │
│              │         │   3. Вызываем BuildFloors(3)         │
│              │         │   4. Комбинируем результаты          │
│              │         │   5. Проверяем валидацию             │
└──────────────┘         └──────────────────────────────────────┘
```

**Недостатки:**

- **Сложность подсистемы**: клиент должен вызывать `FoundationService.BuildFoundation()`, `RoofService.BuildRoof()`, `FloorService.BuildFloors(floorCount)`, а затем вручную комбинировать результаты
- **Знание деталей**: клиент знает о трёх сервисах, порядке их вызова и правилах валидации (например, `floorCount > 0`)
- **Смешение ответственности**: клиент отвечает не только за бизнес-логику, но и за координацию работы подсистемы
- **Хрупкость**: при добавлении нового шага (например, `WallService.BuildWalls()`) клиент нужно менять везде, где вызывается сборка дома

> ✅ Клиент должен вызвать один метод `BuildHouse()` — а не знать о `FoundationService`, `RoofService`, `FloorService`.  
> ❌ Проблема — когда клиент координирует работу множества сервисов подсистемы.

## Решение

Фасад — простой интерфейс, который скрывает сложность подсистемы за одним методом:

```
Клиент                    Фасад                       Подсистема
┌──────────────┐         ┌──────────────────┐        ┌─────────────────────┐
│ Client       │         │ HouseFacade      │        │ FoundationService   │
│              │         │                  │        │ RoofService         │
│ BuildHouse() │───────→ │ BuildHouse()     │──────→ │ FloorService        │
│              │         │                  │        │                     │
│              │         │ + BuildHouse()   │        │ BuildFoundation()   │
└──────────────┘         │                  │──────→ │ BuildRoof()         │
                         │                  │──────→ │ BuildFloors()       │
                         └──────────────────┘        └─────────────────────┘
```

**Фасад** — скрывает сложность подсистемы, предоставляя один метод `BuildHouse()`.  
**Подсистема** — набор сервисов (`FoundationService`, `RoofService`, `FloorService`), которые фасад координирует.

> Клиент вызывает один метод `houseFacade.BuildHouse(floorCount: 3)` — фасад сам вызывает все сервисы в нужном порядке, валидирует входные данные и возвращает готовый результат.

### Как работает

```
Клиент:
  houseFacade.BuildHouse(floorCount: 3)

Фасад внутри:
  1. _foundationService.BuildFoundation()     → Foundation
  2. _roofService.BuildRoof()                 → Roof
  3. _floorService.BuildFloors(3)             → [Floor{1}, Floor{2}, Floor{3}]
  4. Валидация: floorCount > 0
  5. Комбинация: new House { Foundation, Roof, Floors }
  6. Возврат готового House
```

**Упрощение интерфейса:**

```
Без фасада (клиент координирует):
  var foundation = new FoundationService().BuildFoundation();
  var roof = new RoofService().BuildRoof();
  var floors = new FloorService().BuildFloors(3);
  var house = new House { Foundation = foundation, Roof = roof, Floors = floors };

С фасадом (один вызов):
  var house = new HouseFacade().BuildHouse(floorCount: 3);
```

## Структура

| Компонент | Описание | Пример |
|-----------|----------|--------|
| **Facade** | Простой интерфейс, скрывающий сложность подсистемы | `HouseFacade` |
| **ISystem** | Интерфейс фасада для тестирования и DI | `IHouseFacade` |
| **Subsystem Classes** | Классы подсистемы, выполняющие реальную работу | `FoundationService`, `RoofService`, `FloorService` |
| **Entity** | Сущности, создаваемые подсистемой | `House`, `Foundation`, `Roof`, `Floor` |

## Преимущества

- **Простота использования**: клиент работает с одним методом, а не с множеством сервисов
- **Снижение связанности**: клиент зависит от фасада, а не от классов подсистемы
- **Централизация логики**: порядок вызова, валидация и комбинация результатов — в одном месте
- **Лёгкость поддержки**: при изменении подсистемы меняется только фасад, а не клиенты

## Когда использовать

- Нужно упростить интерфейс сложной подсистемы
- Нужно ограничить доступ клиентов к компонентам подсистемы
- Хочется снизить связанность между клиентом и подсистемой
- Нужна точка входа для подсистемы в архитектуре приложения

## Связь с другими паттернами

- **Decorator** — Decorator расширяет интерфейс объекта, а Facade упрощает интерфейс подсистемы
- **Singleton** — фасад часто реализуется как одиночка, если подсистема должна быть единственной
- **Abstract Factory** — фасад может использовать Abstract Factory для создания связанных объектов подсистемы

# Паттерн Прокси (Proxy)

## Описание

**Прокси (Proxy)** — структурный паттерн проектирования, который предоставляет объект-заглушку, контролирующее доступ к реальному объекту, добавляя дополнительное поведение без изменения кода самого объекта.

## Проблема

```
Клиент                    Реальный объект
┌──────────────┐         ┌──────────────────────┐
│ Client       │         │ RemoteService        │
│              │         │                      │
│ Request()    │───────→ │ Request()            │
└──────────────┘         └──────────────────────┘
```

**Недостатки:**

- **Нет контроля доступа**: клиент вызывает реальный объект напрямую — нет проверки прав, логирования или кеширования
- **Нет ленивой инициализации**: реальный объект создаётся всегда, даже если результат не нужен
- **Нет разделения ответственности**: реальный объект должен заниматься не только бизнес-логикой, но и установкой соединений, проверками, кешированием
- **Нарушение SRP**: `RemoteService` отвечает и за обработку запроса, и за управление соединением, и за логирование

> ✅ Клиент должен работать через прокси, который контролирует доступ к реальному объекту.  
> ❌ Проблема — когда клиент вызывает `RemoteService` напрямую и не знает об установлении соединения.

## Решение

Обёртка-прокси, которая контролирует доступ к реальному объекту, делегируя вызов после выполнения дополнительных действий:

```
Клиент                    Прокси                      Реальный объект
┌──────────────┐         ┌──────────────────┐        ┌─────────────────────┐
│ Client       │         │ RemoteService    │        │ RemoteService       │
│              │         │ Proxy            │        │                     │
│ Request()    │───────→ │ Request()        │──────→ │ Request()           │
│              │         │                  │        │                     │
│              │         │ + Установка      │        │ Обработка запроса   │
│              │         │   соединения     │        │   и возврат ответа  │
│              │         │ + Отправка       │        │                     │
│              │         │ + Логирование    │        │                     │
└──────────────┘         └──────────────────┘        └─────────────────────┘
```

**Прокси** — объект, реализующий тот же интерфейс `IRemoteService`, что и реальный объект.  
**Реальный объект** — `RemoteService`, который занимается только бизнес-логикой — обработкой запроса.

> Прокси устанавливает соединение, отправляет запрос, получает ответ и логирует — клиент работает только с `IRemoteService`, не зная, что за ним стоит прокси.

### Как работает

```
Клиент: proxy.Request("{id:10}")

1. Прокси: "[Proxy] Установка соединения с удалённым сервисом..."
2. Прокси: "[Proxy] Отправка запроса на сервер..."
3. Реальный объект: "[RemoteService] Обработка запроса: {id:10}"
4. Реальный объект: возвращает "Ответ на '{id:10}'"
5. Прокси: "[Proxy] Получен ответ от сервера."
6. Прокси: возвращает ответ клиенту
```

**Прозрачность для клиента:**

```
Клиент работает с интерфейсом IRemoteService:

  IRemoteService service = new RemoteServiceProxy();  // прокси
  IRemoteService service = new RemoteService();        // реальный объект

  service.Request("{id:10}");  // одинаковый вызов
```

Клиент не знает, работает ли он с реальным объектом или с прокси — интерфейс одинаковый.

## Структура

| Компонент | Описание | Пример |
|-----------|----------|--------|
| **ISubject** | Общий интерфейс для реального объекта и прокси | `IRemoteService` |
| **RealSubject** | Реальный объект с основной бизнес-логикой | `RemoteService` |
| **Proxy** | Объект-заглушка, контролирующий доступ к реальному объекту | `RemoteServiceProxy` |

## Преимущества

- **Контроль доступа**: прокси может проверять права, валидировать входные данные
- **Ленивая инициализация**: реальный объект создаётся только при первом запросе
- **Дополнительное поведение**: логирование, кеширование, аутентификация без изменения реального объекта
- **Прозрачность**: клиент работает с тем же интерфейсом — не знает, реальная ли это ссылка или прокси
- **Принцип единственной ответственности**: реальный объект занимается бизнес-логикой, прокси — дополнительными действиями

## Когда использовать

- Нужно контролировать доступ к удалённому или ресурсоёмкому объекту
- Нужно ленивое создание (виртуальный прокси) — создавать объект только при первом запросе
- Нужно кеширование результатов (прокси кеширования)
- Нужно логирование, аутентификация или валидация перед вызовом реального объекта

## Связь с другими паттернами

- **Decorator** — оба оборачивают объект для добавления поведения. Decorator добавляет *новые* поведения, а Proxy контролирует *доступ* к объекту
- **Facade** — Facade упрощает интерфейс подсистемы, а Proxy предоставляет тот же интерфейс, но с контролем доступа
- **Singleton** — прокси часто кеширует один экземпляр реального объекта (ленивая инициализация)
